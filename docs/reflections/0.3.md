## Requirement evidence

### Product applications

- Settings is a real persisted two-page workflow. It separates committed and
  candidate state, validates before apply, persists before replacing committed
  state, and exercises Apply/Cancel plus both pages in
  `mwtl.settings_application_gui`. The model test covers missing, round-trip,
  malformed, and unknown registry schemas.
- Hot Corners is a real multi-monitor tray utility. It projects commands to the
  menu and accelerators, persists settings and placement, decodes typed tray
  callbacks, recreates after `TaskbarCreated`, and removes deterministically.
  Its GUI self-test now reads MSAA names, proves the Ctrl+E command projection,
  checks DPI fonts/layout, drives system appearance refresh, and closes through
  the production path.
- The property-sheet path covers multi-page navigation, native dirty/apply
  enablement, validation veto, Apply/OK/Cancel, modal and modeless lifetime,
  callback exceptions, responsive page geometry, cross-thread close requests,
  and repeated creation/destruction.
- Explorer composes Rebar, image-backed Toolbar, Tabs, Splitter, TreeView,
  owner-data ListView, StatusBar, ImageList, shared commands/accelerators, and
  context menus. Its application-owned model keeps stable folder/file IDs
  across filtering and sorting. The real executable proves owner-data mapping,
  pane notification forwarding, tabs, F5, context routing, MSAA names, system
  appearance refresh, geometry, and bounded menu resources.
- The reference-app index maps Settings, Explorer, Hot Corners, and Notepad to
  direct keyboard, accessibility, DPI/High Contrast, manifest, model, native,
  GUI, and package evidence. These applications persist settings, edit files,
  navigate data, or perform background utility work; none is merely a control
  screenshot.

### Reusable library contracts

- `Splitter` owns its focusable container and borrows two direct-child panes;
  its HWND-free model resolves constraints in DIPs. It supports mouse and
  keyboard positioning, exposes an MSAA slider, and forwards pane `WM_NOTIFY`,
  control-originated `WM_COMMAND`, and `WM_CONTEXTMENU` to its parent with exact
  parameters and results.
- `TabWorkspaceModel` and `TabControl` use stable nonzero `TabId` values and
  preserve selection independent of native indices. The Explorer audit caught
  and fixed an accidental integer-index overload in its self-test by requiring
  explicit `TabId{1}` at the ambiguous call site.
- Property-page/sheet APIs retain page state independently of lazy HWNDs,
  define validation/dirty/apply/reset semantics, capture callback exceptions,
  and provide deterministic modal/modeless results and teardown.
- Task dialogs cover custom buttons, radio/verification state, links, progress,
  callback events, keep-open, cancellation, availability, HRESULT failures,
  and callback exception containment.
- General dialogs are move-only, borrow their owner, own modeless HWND state,
  use native modal loops, support normal retained layouts, distinguish all
  results, and marshal cross-thread close requests without permitting arbitrary
  cross-thread UI access.
- `TrayIcon` is move-only and owns one Shell registration while borrowing its
  owner and HICON. `TrayIconStateModel` is now the same HWND-free state machine
  used by the wrapper for initial add, added state, retryable Explorer recovery,
  and detach.
- Tooltip, ImageList, and Menu document native ownership and transfer. Toolbar
  image-list attachment is borrowed. Popup results distinguish selected,
  cancelled, and failed tracking.
- TreeView/ListView use stable typed IDs, typed notifications, exception-safe
  sorting, multi-selection, edit/state APIs, and an application-authoritative
  virtual model without native application pointers.
- `SelectionAdapter` owns labels/typed values apart from native item data,
  checks bounds and synchronization, and requires exclusive UI-thread mutation.
- Resizable property pages and dialogs use the ordinary retained layout system;
  0.3 did not introduce a competing anchor layout.
- Public headers and `docs/api.md` state UI-thread rules, owned/borrowed
  lifetimes, structured and last-error failures, borrowed native escape hatches,
  callback/view expiry, Windows 10+ assumptions, and best-effort availability.

## Defects found during completion audit

1. Explorer initially placed TreeView/ListView under Splitter without realizing
   that their `WM_NOTIFY` reached the container rather than the top-level
   handler. Owner-data text and selection routing therefore depended on an
   invalid composition assumption.
2. Explorer's functional tab self-test passed `SetSelection({1})`; overload
   resolution selected native index 1 rather than stable ID 1.
3. The first local rerun used a wrong CMake target name, after which CTest ran an
   old executable. The stale binary passed and temporarily hid the tab defect.
4. Tray behavior had a real Shell integration test but no pure state test,
   contradicting an explicit acceptance item.
5. The first state-model extraction transitioned before validating `Add`
   arguments, leaving an invalid call in recovery state. The existing native
   test caught the regression at exact exit code 3.
6. Reference applications applied system appearance at creation but Settings,
   Explorer, and Hot Corners lacked direct runtime High Contrast/theme refresh
   evidence. Hot Corners' old self-test only fired one action and closed.
7. The clang-cl workflow excluded two older GUI self-tests whose binaries cannot
   activate on the hosted image, but not the newly added Settings and Explorer
   GUI tests. clang compiled them successfully, then failed to launch them with
   Win32 14001.
8. One local Release full run observed a single `mwtl.desktop` failure. The test
   immediately passed alone and the complete Release suite then passed; the
   current post-audit full run also passes. This is recorded as desktop-global
   state sensitivity, not silently erased.
9. The first ARM64 CI attempt ran 101/102 compatible tests successfully but the
   PowerShell GUI-test host hit an internal CLR error while starting Settings.
   A failed-job rerun rebuilt the same SHA and passed the complete ARM64 gate;
   no C++ assertion or repeatable application crash was observed.

  context menus, with exact native result/parameter assertions.

  step-specific GUI failure codes, and freshly rebuilt binaries for verification.
- `TrayIconStateModel` was added, wired into `TrayIcon`, documented and indexed,
  and covered by a separate pure test. Validation now precedes the state change.
- Settings, Explorer, and Hot Corners reapply system appearance on theme/system
  changes. Their GUI tests read additional MSAA names; Hot Corners also verifies
  accelerator projection, DPI fonts, and retained geometry.
- Reference documentation now has a per-application release-quality evidence
  matrix and points the document reference to the full Notepad application.
- clang-cl remains a compile and non-GUI compatibility gate; the four real GUI
  self-tests run completely in the primary VS2026/MSVC Debug and Release jobs.

## Known limitations intentionally deferred

- mwtl targets Windows 10 1809+, C++20, Unicode, and modern MSVC. It does not
  reproduce Win32++ source/API compatibility or pre-Windows-10 workarounds;
  these are explicit project non-goals and do not remove any 0.3 scenario.
- clang-cl GUI executables are compiled but their four executable self-tests are
  not launched on the hosted clang image because its side-by-side runtime cannot
  activate them. The exact same sources run in both primary VS2026/MSVC x64
  configurations; clang still builds every target and runs all compatible
  model/native/metadata/package tests.
- ARM64 runs natively on the remote Windows ARM runner and passes every
  compatible model/native/GUI/package test; only notification-area tests are
  excluded because that runner has no usable Explorer tray. Real Shell protocol
  remains covered in both primary x64 matrices.
- Direct2D/custom rendering, embedded third-party HWNDs, printing, drag/drop,
  richer Shell integration, multi-document workspaces, docking, Ribbon, and
  legacy MDI belong to 0.4–0.8. None is named in the 0.3 acceptance contract.
- Real accessibility validation uses native MSAA names/roles/states and Windows
  control behavior; a full external screen-reader certification pass is not a
  0.3 requirement.
