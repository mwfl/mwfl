# 0.7 reflection — docking workspace

> Historical snapshot: see the [current support evidence](README.md) before
> relying on deferred-work notes in this milestone record.

## Requirement evidence

### Product evidence

1. `examples/docking_workspace` is a distributable Per-Monitor-V2 IDE-style
   application with two document tabs, left and bottom tool groups, nested
   constrained splitters, a floating tool host, auto-hide/pin commands, native
   previews, pointer and keyboard docking, layout save/reset/restore, tab
   reorder, panel close, and stable-ID restore. Its offline self-test performs
   float/redock, auto-hide/pin, mouse commit/cancel, keyboard navigation/accept,
   reorder, close/restore, persistence, monitor recovery, and ordered shutdown.
2. Pointer docking starts only after the Windows drag threshold and capture,
   translates the accepted target into a non-mutating model proposal, shows a
   nonactivating transparent preview, and adopts only on release. Escape,
   capture loss, tab destruction, invalid targets, adoption failure, stale
   transactions, reentrancy, and callback exceptions retain the source.
   `DockKeyboardSession` exposes the same logical target vocabulary with arrows,
   Tab/Shift+Tab, Enter, Escape, and accessible announcements.
3. `DockFloatingWindow`, `RecoverDockFloatingPlacement`, and
   `DockAutoHideController` cover owned auxiliary-window shutdown, borrowed
   content restoration, DPI/minimum-size handling, removed-monitor recovery,
   focus-held-open behavior, bounded timing, and explicit pin/command paths.
   The audit fixed `WindowBase` so WTL's inherited `WM_DESTROY` handler cannot
   bypass `quit_on_destroy=false`.
4. `SerializeDockingSession`, `ParseDockingSession`, atomic file helpers, and
   the reference application's stable-ID resolver preserve logical state only.
   Malformed, oversized, duplicate, cyclic, unknown-required-version, missing
   panel, and invalid-monitor candidates cannot partially mutate the workspace.

### Reusable library evidence

1. `docking_workspace.h/.cpp` defines nonzero panel/group/node/floating IDs,
   document/tool roles, group and split nodes, floating and auto-hide state,
   deterministic active fallback, ratios, explicit typed mutations, proposals,
   revision checks, graph validation, and commit/replace boundaries. The model
   owns no HWND, callback, or panel content.
2. `docking_native.h/.cpp` borrows same-process, creating-thread HWNDs and
   records parent, styles, visibility, and focus in adoption plans. Prepare is
   non-mutating; Adopt is rollback-capable until Commit. The final application
   audit found that logically closed bound HWNDs were not in the plan; the
   adapter now parks/hides them transactionally and the native test proves both
   rollback and commit.
3. `docking_drag`, `docking_preview`, and `docking_keyboard` keep input and
   feedback out of the model. `docking_floating`, `docking_auto_hide`, and
   `docking_monitor` keep auxiliary-window, timer, and monitor policy explicit.
   `docking_session` is a separate bounded pointer-free I/O boundary and calls
   no application UI callback while holding an I/O lock.
4. Public header comments plus `docs/api.md`, `docs/reference.md`, the beginner
   tutorial, recipes, development architecture, API index, capability manifest,
   llms-full, website, and Win32++ comparison state Windows 10+/C++20 scope,
   ownership, thread affinity, callback/reentrancy rules, DIP coordinates,
   monitor trust, failure statuses, persistence bounds, raw HWND interop, and
   document/command/tab/splitter composition.

### Automated evidence

1. `mwfl.docking_workspace` covers IDs, duplicate/missing/role errors, move and
   reorder, tab/split/float/auto-hide/close, ratio bounds, active fallback,
   stale proposals, cycle rejection, and deterministic logical state.
2. `mwfl.docking_drag`, `mwfl.docking_keyboard`, and
   `mwfl.docking_preview_native` cover overlapping target priority, disabled and
   invalid targets, proposal cancellation, adoption/callback failure,
   reentrancy/stale commit, Escape, spatial/sequential navigation, accessible
   descriptions, focus preservation, high contrast, DPI, nonactivation, and
   repeated preview creation/destruction.
3. `mwfl.docking_native` covers binding/process/thread/stale HWND rules,
   reparent/style/visibility/focus adoption, rollback, auto-hide parking,
   transactional close parking, teardown, and repeatable detach.
   `mwfl.docking_floating_native` covers DPI, minimum size, close actions,
   callback exceptions, content restoration, repeated close/destroy, and no
   process quit.
4. `mwfl.docking_session` covers deterministic round trip, version migration,
   optional fields, truncation, malformed/oversized/duplicate/cyclic state,
   atomic isolated-file I/O, and cleanup. `mwfl.docking_monitor` uses injected
   work areas/DPI and removed/off-screen monitor cases without requiring a
   second display.
5. `mwfl.docking_stress_native` runs 200 move, auto-hide/pin, drag-cancel,
   serialization/parse, and floating create/show/hide/destroy cycles, rejects a
   panel destroyed between prepare and adoption, repeats detach/destroy, and
   enforces a maximum +4 USER/+4 GDI resource delta after warmup.
6. `mwfl.docking_workspace_gui` executes the composed native workflow without
   network or dialogs. `mwfl.package_consumer` compiles the docking surface from
   installed, `add_subdirectory`, and `FetchContent` consumption without
   acquiring optional rendering, OLE, or Shell components. Independent-header,
   manifest, documentation, site-link, metadata, architecture, and build-budget
   checks run in the complete gate.
7. Agent task 30 and `agent-evals/fixtures/docking_workspace.cpp` compile a
   public-API-only golden fixture and explicitly reject pointer/HWND
   serialization, hidden global state, model-owned HWNDs, source-first moves,
   pixel-only layouts, pointer-only access, stale callbacks, partial shutdown,
   and exceptions crossing Win32.

## Defects found

1. The first reference application compiled but did not implement a real mouse
   path. The audit added Tab subclassing, the system drag threshold, capture,
   screen-DIP target updates, proposal/preview separation, transactional release,
   and Escape/capture/destruction cancellation, then registered the GUI self-test
   in CTest.
2. The first application evidence did not directly prove reorder and close.
   Commands, shortcuts, self-test steps, and tutorial instructions now cover
   tab reorder, close, and stable-ID restore.
3. Closing a logical panel omitted its still-bound HWND from native adoption.
   `DockNativeWorkspaceAdapter::Prepare` now adds absent bound panels as hidden
   moves to the parking parent; native tests prove rollback and committed close.
4. A complete Debug run exposed WTL's inherited frame `WM_DESTROY` handler
   posting `WM_QUIT(1)` even when mwfl configured an auxiliary window with
   `quit_on_destroy=false`. `Window::ProcessWindowMessage` now consumes that
   inherited handler and `SafeWindowProc` alone applies the explicit instance
   policy. The focused test passed 100 consecutive process runs before the full
   gates were repeated.
5. The build budget still described the pre-docking archive. The nine measured
   VS2026 x64 Debug docking objects total 6,131,009 bytes; the complete Debug
   archive measures 25,233,412 bytes and Release 8,936,512 bytes. The budget is
   now an explicit 26 MiB regression ceiling (under 8% headroom), and the core
   header ceiling is 200 KiB against a measured 190,071 bytes. This records the
   deliberate capability cost instead of silently disabling the guard.
6. Initial documentation metadata used two invented names
   (`DockNativeAdapter`, `DockingSessionStore`) and obsolete test names. The
   manifest was corrected to exact public symbols and registered CTest names;
   API-index and example-catalog validators pass.

## Known limitations

1. The reference app is intentionally small: it uses raw EDIT/LISTBOX content
   and application-composed TabControl/Splitter hosts, not a mandatory framework
   shell or Document/View hierarchy. This does not limit the public docking
   graph or native adapter and keeps ownership visible.
2. Split minimum sizes are enforced by the composed `Splitter` and floating
   host, while the pointer-free docking graph stores bounded ratios rather than
   native pixel constraints. This is intentional separation: minimum layout is
   DPI-aware host policy, and persisted state remains monitor-independent.
3. Real multi-monitor placement is tested through injectable topology because a
   second physical monitor is not deterministic. Native `WM_DPICHANGED` and
   virtual-screen APIs still have direct native tests.
4. The compatibility/CI matrix is not a 0.7 limitation claim: it is explicitly
   scheduled after 0.8 and therefore cannot be inferred from the x64 VS2026
   evidence above.

## Thoroughly complete?

**Yes, for the explicitly approved 0.7 scope.** Every acceptance checkbox has a
direct implementation, reference application, documentation/Agent retrieval
path, and named automated proof. The final audit found and fixed issues that
narrow testing had missed, then rebuilt and passed all 153 tests in both VS2026
x64 Debug and Release. No 0.8 work began before this conclusion. Deferred
architectures, compilers, and CI are recorded rather than represented as green.
