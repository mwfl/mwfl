# 0.8 reflection — optional traditional Windows integrations

> Historical snapshot: see the [current support evidence](README.md) before
> relying on deferred-work notes in this milestone record.

## Requirement evidence

### Product evidence

1. `examples/ribbon_workspace` is a Unicode, Per-Monitor-V2 UICC-backed
   application. It binds generated Ribbon IDs to `CommandSet`, changes modes
   and contextual visibility, copies bounded recent items, provides Keytips,
   handles DPI and theme changes, persists settings, reports framework absence
   without a dialog, and has a deterministic offline GUI self-test.
2. `examples/mdi_workspace` creates a native MDICLIENT and multiple child
   frames, uses stable `MdiChildId` values, routes menu and accelerator commands
   to the active child, activates/cascades/tiles children, gathers all dirty
   close decisions before mutation, and tears down without a global current
   document or a child-posted process quit. The tutorial explicitly recommends
   `DocumentWorkspaceModel` and docking for new products.
3. `examples/graphics_interop` records, saves, loads, and plays an enhanced
   metafile and exports bounded PNG output through GDI+. Its callbacks receive
   borrowed HDC/`Gdiplus::Graphics` values and the application retains no
   callback-scoped object. Its GUI self-test checks both formats and cleanup.
4. `examples/shell_integration` demonstrates stable taskbar thumbnail commands
   and tabs, reapplication after `TaskbarCreated`, validated contextual Help,
   structured unavailable/error/cancelled results, and injected offline Help.
   Reference manifests and CMake install rules make all four applications
   distributable on Windows 10+ without a network-dependent self-test.

### Reusable library evidence

1. `mwfl::ribbon` is an exported optional component. `RibbonCommandModel`
   stores pointer-free command/mode/context/recent metadata;
   `RibbonFrameworkHost` borrows the HWND, model, and `CommandSet`, owns its COM
   callbacks, exposes a borrowed `IUIFramework*`, checks the creating STA, maps
   absence and HRESULT failures, contains callback exceptions, and destroys in
   STA order. The final audit fixed wrong-thread `Destroy` so it is a no-op
   rather than releasing apartment-affine COM state.
2. `mwfl::mdi` is an exported optional compatibility component.
   `MdiWorkspaceModel` owns stable metadata while `MdiHost` owns only client and
   child HWND infrastructure and borrows frame/model/callback state. It checks
   thread/process identity, contains child exceptions, handles external child
   destruction, composes with menu/accelerator/default-frame routing, and does
   not impose MDI on document, docking, command, or core consumers.
3. `mwfl::graphics` defines move-only `HENHMETAFILE` ownership, explicit
   `GdiPlusSession` token ownership, callback-scoped drawing objects, checked
   frame/pixel units and integer bounds, balanced record/playback/save/load,
   bounded pixel allocation, and atomic sibling replacement. Exceptions return
   structured results and incomplete output is removed.
4. `mwfl::shell` taskbar additions remain creating-UI-thread COM state, borrow
   HWND/HICON values, use stable application IDs, support repeated clear/reset
   and Explorer recreation, and expose structured unavailable/rejected/COM
   results. `help.h` permits only absolute local CHM/HTML or credential-free
   HTTPS, rejects traversal and command construction, and supports an injected
   backend for cancellation/failure/offline tests.
5. `mwfl::ribbon`, `mwfl::mdi`, and `mwfl::graphics` are separate exported
   targets; Help is header-only and Shell-scoped. Core consumers link none of
   their system libraries, generate no Ribbon resources, initialize no COM or
   GDI+ state, and keep the measured core header surface at 190,071 bytes.
   Public header comments and API/architecture documentation state Windows
   10+, C++20, ownership, affinity, reentrancy, units, trust, errors, teardown,
   native escape hatches, and modern alternatives.

## Defects found

1. The first Agent Ribbon fixture returned the successful `Create` result when
   `Load` failed. It now returns the actual load failure, and both fixture
   configurations compile.
2. The first taskbar/Help fixture called `Recreate` after Explorer restart but
   did not reapply its thumbnail buttons. It now stores stable button metadata
   and reapplies it after recreation.
3. Native Ribbon tests initially lacked direct wrong-thread teardown and missing
   resource evidence. Adding them exposed that `RibbonFrameworkHost::Destroy`
   skipped `IUIFramework::Destroy` on a worker but still released COM references
   and erased state there. Wrong-thread `Destroy` is now fully non-mutating and
   the creating STA completes teardown; Debug and Release tests prove it.
4. Native MDI tests did not directly prove cross-thread rejection, cleanup after
   external HWND destruction, or absence of premature process quit. The 50-cycle
   test now asserts each boundary in both configurations.
5. The complete Debug gate found the four new optional headers misclassified as
   core, reporting 206,944 bytes against the 200 KiB core ceiling. The verifier
   now classifies Ribbon/MDI/graphics/Help as optional: core remains 190,071
   bytes. The measured optional surface is 69,781 bytes with a documented 72
   KiB regression ceiling; the core budget was not relaxed.

## Known limitations

1. Windows Ribbon Framework availability depends on the host Windows image and
   valid generated UICC markup. Absence and markup failure are structured and
   the reference has a classic-menu fallback, so optional capability does not
   prevent the application or core library from working.
2. MDI is intentionally a compatibility component, not the default document
   architecture. It does not reproduce historical Win32++ API signatures or
   store application document objects. Stable-ID composition proves the needed
   scenario while preserving the Windows 10+/C++20 design objective.
3. GDI+ export is deliberately bounded and PNG-focused rather than a general
   image framework. Raw GDI+/HDC escape hatches remain available inside scoped
   callbacks, satisfying interoperability without hidden ownership.
4. Help tests do not launch a browser or require network access. Validation and
   an injected backend prove trust and result semantics deterministically;
   native Shell execution remains a thin structured adapter.
5. The compiler, architecture, and CI matrix is not inferred from x64 results.
   It is explicitly the next phase and remains outside the approved 0.8 local
   feature gate.

**Yes, for the explicitly approved 0.8 feature scope.** Every checklist item has
a named optional implementation, distributable reference, beginner/Agent path,
and executable evidence. The completion audit found and fixed five evidence or
implementation defects, including a real wrong-thread COM teardown bug, then

Core linkage and header budgets remain isolated. The deliberately deferred
compatibility/architecture/CI phase is recorded and begins only after this 0.8
