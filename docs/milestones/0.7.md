# 0.7 acceptance checklist — docking workspace

0.7 is complete only when every requirement below has direct evidence. A
splitter with movable children is not a docking system, and serialized HWNDs or
pixel rectangles are not a portable workspace layout.

## Product evidence

- [x] A useful IDE-style reference application composes document regions and
  tool panels with docked, tabbed, split, floating, and auto-hidden states.
- [x] Mouse and keyboard workflows dock, undock, reorder, resize, activate,
  float, pin, auto-hide, restore, and close panels without losing stable panel
  identity, application state, focus, commands, or document ownership.
- [x] Dragging presents native, DPI-correct, high-contrast-safe docking targets
  and a non-destructive preview; cancellation or failed adoption restores the
  exact source layout and focus.
- [x] Floating tool windows work across multiple monitors and DPI transitions,
  remain reachable after monitor removal or resolution changes, and do not post
  process quit while the coordinated main workspace remains alive.
- [x] Saved layouts restore logical panel/group/split/floating/auto-hide state
  incrementally, reject malformed or hostile state, and provide a deterministic
  safe default when panels, monitors, or optional tools are unavailable.
- [x] The reference application is Per-Monitor V2, keyboard operable,
  accessible at native boundaries, distributable, and has a deterministic
  offline self-test covering save/restore, redocking, cancellation, and clean
  shutdown.

## Reusable library evidence

- [x] Public docking models use stable nonzero IDs for panels, groups, split
  nodes, and floating hosts; express document/tool roles and docked/tabbed/
  split/floating/auto-hide states without owning contents or HWNDs.
- [x] Layout mutations are explicit validated transactions with typed failures,
  cycle prevention, deterministic active/focus fallback, minimum-size rules,
  and rollback after destination/adoption or callback failure.
- [x] Native adapters borrow panel HWNDs, validate same-process/UI-thread and
  parentage rules, project model state without storing C++ pointers in native
  item data, and define focus, notification, DPI, accessibility, and teardown
  contracts.
- [x] Drag sessions separate hit testing, proposed logical mutation, preview,
  and commit; pointer capture loss, Escape, window destruction, reentrancy, and
  callback exceptions cancel safely without half-committed layout.
- [x] Floating and auto-hide hosts have explicit ownership and activation
  policy, bounded timer/animation behavior, keyboard alternatives, monitor/DPI
  recovery, and coordinated shutdown semantics.
- [x] Docking layout persistence is versioned, bounded, atomic where possible,
  pointer/HWND free, tolerant of unknown optional fields, rejects malformed or
  oversized graphs, and invokes application panel resolvers outside I/O locks.
- [x] Public APIs document Windows 10+, ownership/lifetime, UI-thread and
  callback/reentrancy rules, coordinate units, monitor trust boundaries,
  persistence/security, failure states, raw HWND interop, and composition with
  document workspaces, commands, tabs, splitters, and retained layout.

## Automated evidence

- [x] Pure model tests cover IDs, add/remove/move/tab/split/float/auto-hide,
  active fallback, document/tool constraints, minimum sizes, cycles, failed
  transactions, undoable proposals, and deterministic serialization ordering.
- [x] Native tests cover drag targets/previews, pointer capture and Escape,
  keyboard docking, focus restoration, HWND adoption/reparenting, tab/split
  notifications, accessibility, DPI transitions, stale HWNDs, and teardown in
  different orders.
- [x] Persistence tests use isolated files and cover round trips, migration,
  unknown versions/fields, malformed/oversized/truncated/cyclic graphs, missing
  panels, invalid monitors/rectangles, interrupted writes, and cleanup.
- [x] Multi-monitor tests use injectable monitor/work-area/DPI descriptions for
  deterministic topology changes and exercise real monitor APIs when available
  without assuming a second physical display.
- [x] Lifecycle/stress tests repeatedly dock, split, tab, float, auto-hide,
  redock, persist, restore, create/destroy floating hosts, cancel drags, and
  close the application with bounded HWND/USER/GDI/file/resource deltas.
- [x] Exception and race tests cover resolver/adoption/preview/commit throws,
  close during drag, panel/window destruction during transfer, repeated close,
  worker completion after close, and reentrant activation without exceptions
  crossing Win32 callbacks or stale command targets.
- [x] The approved local gate passes with Visual Studio 2026/MSVC C++20 x64 in
  Debug and Release, including package consumers and documentation checks.
  VS2022, ARM64, other compilers, sanitizers, coverage, Pipeline, and GitHub
  Actions remain deferred until after 0.8.

## Packaging, documentation, and Agent evidence

- [x] Docking core/native/persistence boundaries and optional dependencies are
  explicit; installed, add_subdirectory, and FetchContent consumers compile the
  public surfaces without acquiring unrelated rendering, OLE, or Shell code.
- [x] A beginner tutorial builds the IDE-style workspace step by step with
  VS2026/MSVC C++20 x64 and explains identity, ownership, transactions, native
  adoption, drag cancellation, floating windows, auto-hide, persistence,
  monitor/DPI recovery, shutdown, and diagnostics.
- [x] Focused recipes cover registering a tool panel, document/tool regions,
  tabbing and splitting, mouse and keyboard docking, floating and redocking,
  auto-hide, layout save/restore, custom targets, and safe shutdown.
- [x] Capability/example manifests, API index, website, llms-full, change
  matrix, architecture boundaries, and Win32++ comparison describe every 0.7
  surface, ownership/failure rule, composition boundary, and verification path.
- [x] Agent evals compile golden fixtures for focused changes and reject HWND or
  pointer serialization, hidden global docking state, model-owned panel HWNDs,
  mutation-before-adoption data loss, pixel-only layouts, inaccessible drag-only
  workflows, stale callbacks, and partial shutdown.

## Completion reflection gate

Before changing 0.7 to `complete` in `docs/parity.json`, create
`docs/reflections/0.7.md` containing the exact required sections:

1. `Requirement evidence` for every checkbox above;
2. `Defects found` during audit and fixes made after apparent completion;
3. `Verification evidence` for the complete approved local gates;
4. known limitations with proof they do not violate 0.7 acceptance;
5. `Thoroughly complete?` with an explicit evidence-backed answer.

0.8 work must not begin until every 0.7 checkbox is complete and the reflection
supports a yes.
