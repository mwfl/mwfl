# 0.4 acceptance checklist — rendering and third-party HWND integrations

0.4 is complete only when every requirement below has direct evidence. A demo
that merely creates a child HWND or clears a render target does not prove a
reusable lifecycle contract.

## Product evidence

- [x] A browser reference application hosts WebView2 as an optional component,
  handles missing runtime/install guidance, asynchronous creation, navigation,
  resize, focus, accelerator handoff, process failure, and deterministic close.
- [x] A code-editor reference application hosts Scintilla as an optional pinned
  component and proves Unicode text, commands, notifications, search/replace,
  dirty state, DPI, accessibility boundaries, and save/load integration.
- [x] A drawing reference application uses the reusable Direct2D host for
  resize, invalidation, device-loss recreation, input, DPI, theme/High Contrast,
  and exportable application-owned drawing data.
- [x] An image-viewer reference application decodes image metadata/pixels,
  renders through the supported 2D or swap-chain path, and proves zoom, pan,
  fit, large-image failure, DPI, color/background policy, and resource recovery.
- [x] Every reference application is keyboard operable, accessible at the
  native/host boundary, distributable, useful beyond a screenshot, and has a
  deterministic self-test that never requires network access or user input.

## Reusable library evidence

- [x] A reusable native-host abstraction defines owned/borrowed HWND lifetime,
  parent destruction, attach/detach, focus and dialog navigation, resize/DPI,
  notification forwarding, subclass teardown, thread affinity, and native
  escape hatches without assuming a specific third-party library.
- [x] COM subscription and asynchronous initialization helpers are move-only,
  revoke exactly once, contain callback exceptions, prevent callbacks after
  teardown, and make owner-thread dispatch/cancellation explicit.
- [x] The WebView2 component is optional and isolated from the core target. It
  pins a reviewed SDK/runtime contract, exposes structured availability and
  initialization results, and does not make package consumers fetch WebView2
  unless requested.
- [x] The Scintilla component is optional and isolated from the core target. It
  pins source/binary identity, uses stable typed notifications and UTF-8/UTF-16
  conversion rules, and documents ownership of documents, loaders, and HWNDs.
- [x] The Direct2D host owns factory/device-dependent resources with explicit
  create/discard/recreate phases, contains paint callbacks, handles
  `D2DERR_RECREATE_TARGET`, and never leaks a BeginDraw/EndDraw transaction.
- [x] The Direct3D swap-chain host defines adapter/device/swap-chain ownership,
  resize/minimize/occlusion/device-loss behavior, frame scheduling, teardown,
  and an escape hatch without imposing a game loop on ordinary applications.
- [x] Rendering and host APIs document errors, threading, callback lifetime,
  reentrancy, DPI units, color space/alpha assumptions, Windows 10+ availability,
  and behavior when optional dependencies or hardware acceleration are absent.

## Automated evidence

- [x] Pure model tests cover host lifecycle transitions, async cancellation,
  zoom/pan/fit math, dirty/document transitions, and device-loss state without
  requiring HWNDs, GPU hardware, WebView2, or Scintilla.
- [x] Native tests read actual parent/child HWND state, focus/tab traversal,
  resize/DPI geometry, forwarded notifications, subclass removal, and teardown
  ordering for the generic host and Scintilla path.
- [x] Rendering tests validate actual Direct2D/Direct3D resources where
  available and deterministic software/model fallbacks otherwise, including
  resize, minimize, occlusion, device loss/recreation, paint exceptions, and
  close-during-render behavior.
- [x] Async/COM tests cover immediate and delayed success, missing runtime,
  failure HRESULTs, cancellation before/after callback registration, nested
  message dispatch, callback exception containment, owner-first teardown, and
  shutdown races.
- [x] Stress tests repeatedly create/destroy hosts, COM subscriptions, browser
  environments/controllers, Scintilla documents, D2D targets/bitmaps, and D3D
  devices/swap chains with bounded USER/GDI/COM/GPU-process resources.
- [x] Tests remain deterministic when run unattended: optional-runtime/hardware
  absence is a structured tested outcome, not an unconditional skip or hang.
- [x] The approved 0.4 local gate passes with Visual Studio 2026/MSVC x64 in
  Debug and Release, including package consumers and documentation checks.
  VS2022, ARM64, clang-cl, ASan, static analysis, coverage, Pipeline, and
  GitHub Actions are intentionally deferred until after 0.8 and are not 0.4
  completion criteria.

## Packaging, documentation, and Agent evidence

- [x] Core `mwtl::mwtl` consumers do not download, link, or deploy WebView2,
  Scintilla, Direct2D, or Direct3D helpers unless the corresponding component is
  requested; every optional component has an installed CMake consumer test.
- [x] Beginner tutorials build the browser, editor, drawing, and image-viewer
  applications from supported templates using Visual Studio 2026/MSVC C++20,
  with offline/self-test alternatives and precise dependency diagnostics.
- [x] Focused recipes cover hosting an HWND, adding a WebView2 navigation
  command, handling a Scintilla notification, drawing a DPI-aware D2D scene,
  and recovering a swap chain after resize/device loss without inventing APIs.
- [x] Capability/example manifests, API index, website, `llms-full.txt`, and
  Win32++ comparison describe every shipped 0.4 surface and identify optional
  dependency, ownership, threading, and fallback constraints.
- [x] Agent evals perform at least the five focused changes above, compile their
  golden fixtures, and include negative cases for dependency/lifetime mistakes.

## Completion reflection gate

Before changing 0.4 to `complete` in `docs/parity.json`, create
`docs/reflections/0.4.md` containing the exact required sections:

1. `Requirement evidence` for every checkbox above;
2. `Defects found` during audit and fixes made after apparent completion;
3. `Verification evidence` for full local and CI gates;
4. known limitations with proof they do not violate 0.4 acceptance;
5. `Thoroughly complete?` with an explicit evidence-backed answer.

0.5 work must not begin until every 0.4 checkbox is complete and the reflection
supports a yes.
