# 0.8 acceptance checklist — optional traditional Windows integrations

0.8 is complete only when each optional integration is useful independently,
keeps the minimum `mwtl::mwtl` dependency surface unchanged, and has direct
runtime, packaging, documentation, and Agent evidence. Modern document and
docking APIs remain the default; Ribbon and MDI are opt-in interoperability.

## Product evidence

- [ ] A complete Ribbon reference application binds Windows Ribbon Framework
  commands to `CommandSet`, supports application modes, contextual visibility,
  recent items, keyboard access, DPI/theme changes, persisted settings, and a
  deterministic no-dialog self-test with structured unavailable fallback.
- [ ] A complete legacy MDI reference application creates an MDI client and
  multiple native child frames, routes active-child commands, arranges and
  activates children, coordinates dirty close decisions, and shuts down without
  global current-document state or partial close.
- [ ] A graphics reference demonstrates enhanced-metafile record/playback and
  bounded GDI/GDI+ drawing/export helpers with explicit HDC/HENHMETAFILE/
  Gdiplus lifetime and failure ownership.
- [ ] A desktop integration reference demonstrates additional taskbar behavior
  and contextual Windows Help launching with availability/error/cancellation
  results, stable identity, quoted paths, and no process-wide hidden state.
- [ ] Every reference is Windows 10+, Unicode, Per-Monitor V2, keyboard
  operable, accessible at native boundaries, distributable, and offline-testable.

## Reusable library evidence

- [ ] Ribbon APIs are an optional component, use the creating STA thread,
  contain COM callbacks/exceptions/reentrancy, map stable command/property IDs
  without storing application pointers in Ribbon state, expose borrowed native
  interfaces explicitly, and define framework-unavailable behavior.
- [ ] Legacy MDI APIs are an optional component that owns only host/client/child
  native infrastructure, borrows application document/view state, uses stable
  IDs, contains child callbacks, and composes with `CommandSet`, document close
  coordination, DPI, menus, accelerators, and docking without requiring MDI.
- [ ] Enhanced-metafile and GDI/GDI+ APIs define ownership for every native
  handle/token/HDC, validate bounds and integer conversions, balance native
  transactions, recover or fail cleanly, and never retain callback-scoped HDCs.
- [ ] Taskbar/help additions define UI-thread/COM rules, Explorer restart and
  unavailable Help behavior, stable IDs, path/URI trust boundaries, reversible
  mutations, structured failures, and repeatable teardown.
- [ ] Optional components do not alter core public headers, link dependencies,
  startup, COM policy, or minimum archive budget unless explicitly requested.
- [ ] Public APIs document Windows 10+, C++20, ownership/lifetime, UI-thread and
  apartment rules, callbacks/reentrancy, native escape hatches, coordinate
  units, security boundaries, error statuses, teardown, and modern alternatives.

## Automated evidence

- [ ] Ribbon model/native tests cover command/property mapping, invalid markup,
  unavailable framework, creation/destruction, modes/context, recent items,
  keyboard/accessibility, DPI/theme/settings, callback exceptions, reentrancy,
  stale interfaces, and repeated initialization/teardown.
- [ ] MDI model/native tests cover stable child identity, create/activate/
  arrange/transfer/close, menu and command routing, dirty coordinated close,
  child failure/destruction orders, reentrancy, stale HWNDs, and no premature
  process quit.
- [ ] Metafile/GDI/GDI+ tests cover empty/large/invalid geometry, record/playback
  and export, ownership transfer, balanced cleanup on every failure, DPI/color/
  transform behavior, callback exceptions, malformed input, and bounded USER/
  GDI/resource deltas.
- [ ] Taskbar/help tests cover Explorer restart, unavailable/rejected COM,
  stable task identity, quoting and untrusted inputs, missing Help content,
  callback failure, repeated clear/close, and deterministic offline behavior.
- [ ] Lifecycle/stress tests repeatedly create/use/destroy every optional host,
  include failure injection and teardown permutations, and enforce bounded
  HWND/USER/GDI/COM/file/resource deltas.
- [ ] Installed, `add_subdirectory`, and `FetchContent` consumers compile each
  optional component independently and prove core consumers acquire none of
  their SDK libraries, generated artifacts, or initialization requirements.
- [ ] The approved local gate passes Visual Studio 2026/MSVC C++20 x64 Debug
  and Release. VS2022, ARM64, clang-cl, sanitizers, coverage/static analysis,
  Pipeline, and GitHub Actions remain deferred until the post-0.8 matrix pass.

## Packaging, documentation, and Agent evidence

- [ ] CMake options, exported component targets, generated Ribbon resources,
  runtime assets, install rules, licenses, cache/offline behavior, and component
  failure diagnostics are deterministic and independently documented.
- [ ] Beginner tutorials build the Ribbon and MDI references step by step with
  VS2026/MSVC C++20 x64 and explain when to choose modern document/docking APIs
  instead; graphics/taskbar/help tutorials cover ownership and safe failures.
- [ ] Focused recipes cover Ribbon command binding/properties/modes/recent items,
  MDI host/child/routing/close, metafile record/play/export, GDI/GDI+ resources,
  taskbar recovery, Help launch, and ordered shutdown.
- [ ] Capability/example manifests, API index, website, llms-full, change
  selector, architecture boundaries, scope map, Win32++ comparison, and parity
  roadmap describe every 0.8 surface and verification path using exact symbols.
- [ ] Agent evals compile golden fixtures and reject mandatory Ribbon/MDI core
  coupling, hidden global active child, pointer/native-interface persistence,
  unbalanced HDC/metafile/GDI+ ownership, callback exceptions across native
  boundaries, unsafe Help paths, stale COM/HWND use, and partial shutdown.

## Completion reflection gate

Before changing 0.8 to `complete` in `docs/parity.json`, create
`docs/reflections/0.8.md` containing:

1. `Requirement evidence` for every checkbox above;
2. `Defects found` during audit and fixes made after apparent completion;
3. `Verification evidence` for the complete approved local gates;
4. known limitations with proof they do not violate 0.8 acceptance;
5. `Thoroughly complete?` with an explicit evidence-backed answer.

The post-0.8 compiler/architecture/CI repair pass and final pull request begin
only after this reflection supports a yes.
