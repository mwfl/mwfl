# mwfl 0.1.1 ecosystem and compatibility milestone

This is the active milestone after the `v0.1.0` public baseline. It is distinct
from the historical capability milestone named `0.2`, whose SDI work shipped
as part of `v0.1.0`.

## Outcome

Prove that the public baseline is consumable as a maintained Windows library,
not only buildable inside this repository. Version 0.1.1 is an ecosystem and
compatibility release; it does not require a new UI component.

## Acceptance checklist

### Public compatibility

- [x] Every installed public header from `v0.1.0` remains present.
- [x] The frozen 0.1 source consumer builds through installed-package,
  `FetchContent`, and `add_subdirectory` acquisition.
- [x] Stable 0.1 signatures are not removed or changed. Any provisional break
  is documented in the 0.1.1 release notes with a migration.
- [x] Deprecations remain available for at least one subsequent minor release.
- [x] Package version checks follow the documented source-compatibility policy;
  ABI compatibility is not claimed.

### Maintained matrix

- [x] VS 2026 x64 Debug and Release build and test.
- [x] VS 2022 x64 Release builds and tests as the compatibility toolchain.
- [x] Native ARM64 Debug builds and tests on the Windows ARM runner.
- [x] Installed package consumers pass for every exported component.
- [x] Static analysis, AddressSanitizer, native coverage, and lifecycle-repeat
  jobs remain required CI evidence.

### Downstream applications

- [x] The eight official applications are described by
  `docs/downstream-consumers.json` with repository, local source-acquisition
  switch, canonical preset, and product role.
- [x] Each application can consume the current MWFL checkout without modifying
  its source tree.
- [x] `.github/workflows/downstream.yml` configures, builds, and tests every
  official application against the candidate MWFL commit.
- [x] A downstream failure blocks the 0.1.1 release.

### Examples and discovery

- [x] The example catalog exposes starter, focused, catalog, advanced, and
  reference paths rather than presenting 62 equivalent starting points.
- [x] Official standalone applications are separate from compiled examples.
- [x] `docs/examples.json`, `examples/README.md`, the root README, Agent index,
  and generated Pages catalog agree.
- [x] New examples require a distinct public contract or canonical composition;
  a small syntax variation belongs in a recipe or an existing example.

### Release

- [x] `PROJECT_VERSION`, templates, package names, release notes, and generated
  Pages copy agree on 0.1.1 only when every preceding gate is green.
- [ ] x64 and ARM64 CMake packages are published with hashes and provenance.
- [x] Release evidence records exact toolchains, configurations, skipped tests,
  and all downstream revisions.

## Stop-ship conditions

- A stable 0.1 consumer no longer compiles.
- Any official downstream application requires an unreviewed workaround.
- A public header disappears from the baseline without a migration.
- Package, documentation, examples, or Agent metadata conflict.
- ARM64 is advertised without native build evidence.

## Evidence commands

```powershell
./scripts/verify.ps1 -Mode Full -VisualStudio 2026 -Architecture x64
./scripts/verify.ps1 -Mode Full -VisualStudio 2022 -Architecture x64
./scripts/verify.ps1 -Mode Full -VisualStudio 2022 -Architecture ARM64
./scripts/verify-downstream.ps1 -MwflSource . -Configuration Release
```

The milestone is complete only when the checklist is backed by current command
output or CI runs. The checklist is not release evidence by itself.
